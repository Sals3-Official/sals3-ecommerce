## Repository and vault

- Canonical repository: `github.com/Sals3-Official/sals3-ecommerce`.
- Local Windows path used in this workspace: `E:\sals3-ecommerce`.
- Obsidian vault root: `docs/`; do not open the repository root as the vault.
- The old standalone `sals3-2nd-brain` repository is deprecated/frozen.
- Next.js + TypeScript application, tests, linting, formatting, Husky, and CI foundations exist.
- `sals3-portal` is a separate repository/local clone. Whenever work touches it or its storefront API, its actual current code, schema, tests, and API contracts are the strict reference.

### Git safety

- Obsidian Git auto-commit/auto-push remains disabled. A prior live test proved a vault commit can sweep application files outside `docs/`.
- Every change goes through a feature/chore/bug branch and pull request; never commit directly to `main` or `develop`.
- Before staging a vault change, verify that only intended paths are included.

## Verified implementation state

### Implemented foundations

- **A variant photo now sticks in the editor and reaches the buyer — 2026-08-25, three merged PRs, no DDL anywhere.** One owner sentence (*"pag nakapag select na ako ng photos ay nawawala din ito agad. pagka publish tapos hindi nag rereflect ang selected photos ko sa store front"*) was **two unrelated defects on one control**. (1) **The write always landed; the read undid it.** Nine action files called `revalidatePath('/listings')` while the Product Editor is `/listings/new?productId=…` and the description studio is `/listings/[productId]/description` — so `assignVariantMedia` committed, the thumbnail appeared from local optimistic state, `router.refresh()` re-requested a route nothing had invalidated, and the stale projection restored the placeholder. `description-actions.ts` alone carried a second literal `revalidatePath('/listings/new')`, which is the entire reason description edits stuck while photo assignment did not. All twelve call sites now go through `revalidateListingViews()` = one `revalidatePath('/listings', 'layout')`, covering the subtree without naming a route: **a list of literals is a list that goes stale silently**, and these paths were not wrong when written, they became wrong when the editor moved to a child route. Two side lessons: `import 'server-only'` in that helper failed nine test files at once (its default export throws outside Next's bundler condition — same reason `read-model.ts` refuses the guard), and the existing assertion `toHaveBeenCalledWith('/listings')` **passes for the broken call**, which is what let it ship. (2) **`StorefrontVariant` had no image field at all** — a per-variant photo was not on the cross-repository wire in any form, and both `primaryImageUrl` and the detail gallery order by `(variant_id is null) desc`, so tagging a photo to a variant actively *demoted* it. Assigning one could only ever make the storefront worse. It now carries `imageUrl` through the same `APPROVED`/rights/`mediaVisibleToBuyers` gate and `coalesce(stored_url, source_url)` precedence as the cover, as a **correlated subquery** so it cannot multiply the variant × option rows; the new `innerJoin(products)` it needs for `show_supplier_photo` cannot drop a variant because `product_variants.product_id` is `notNull` with an FK. **`shareFirstAxisPhotos` resolves it per option group before it goes on the wire** — `variant_id` is one column and the checksum index forbids a second row for the same file, so the group control writes a colour's photo onto one variant, and serving that raw puts a picture on `Black · S` and nothing on `Black · M`. Grouped on axis name **and** value (`Colour: Natural` ≠ `Material: Natural`), on **the axis the seller arranged first** rather than "the colour one", and it never overwrites a photo assigned to that exact variant. Product cache key `v5` → `v6`; the feed key stays `v2` because a card row has no variants. (3) **`VariantValuePhotoStrip`'s lock lost its reason and went with it** — its doc comment said a shared value's photo would "leave the other three Black variants photoless on the storefront", which `shareFirstAxisPhotos` makes false, and a false rationale is part 69's `fetchProductReviews` failure repeated deliberately. It also resolved an older contradiction: the Variants & Pricing rail has always written a group photo this way, and on a `Colour × Size` product the strip previously rendered **nothing at all**. **Two regressions were introduced by this work and caught only in the pre-merge re-read, both after three green CI runs**: the consumer's `variants` is a `salvagedArray`, so a malformed `imageUrl` dropped the whole variant — costing a buyer a purchasable size to avoid a missing thumbnail, fixed with `.catch(undefined)`; and `ProductRecordPanel.handlePopState` never dispatches `PRODUCT_VARIANT_CHANGE_EVENT`, so the gallery followed the chips but not the back button. Also merged the same day: **the description studio opens in the v3.1 canvas layout** — `heading · paragraph · image · bulletList · image · image · keyValueList` read off the `.dc.html` source, replacing three category templates **none of which contained an `image`**; safe to apply by default because `prepareBlocksForSave` drops every empty block, so opening and leaving stores the same empty document. `verify` green on both merged `develop` branches (**2,550 unit / 79 e2e** portal, **815 unit / 37 e2e** ecommerce), zero drift at merge time, contract fixture byte-identical. **Not proven against real rows**: no published product exists locally and the preview is behind deployment protection, so assign → publish → buyer has never run end to end. See [[sals3-session-2026-08-25-part71-the-variant-photo-that-vanished-and-the-wire-that-could-not-carry-it]]. `sals3-portal` [#179](https://github.com/Sals3-Official/sals3-portal/pull/179)/[#180](https://github.com/Sals3-Official/sals3-portal/pull/180) and `sals3-ecommerce` [#153](https://github.com/Sals3-Official/sals3-ecommerce/pull/153), all merged.
- **Variants & Pricing reworked over five merged `sals3-portal` PRs, with no DDL at all — 2026-08-22.** One owner request (*"adapt this style"*, pointing at a marketplace seller centre's Variations editor) became five PRs of owner-corrected iteration, and `git diff` over `src/lib/db` and `drizzle/` is empty across every one of them — `0027_many_lockjaw.sql` is still the latest migration. **The table's final shape for a mapped product** is `Colour · List · Size · Sals3 SKU · Supplier cost · Retail price · Supplier stock · Attention`: the first axis leads and its cell is a rail carrying the group's photograph, rows of one colour merge into it `rowSpan`-style with `4 × Size` under the name, the separate `Image` column is gone (one colour is one photograph), and the axis name is the header so the cell holds the value alone. An unmapped product is untouched — `BASE_COLUMNS` with `Image` and one `Variant` column, the supplier's label whole. **The Variant Matrix** gained one card per axis from one component (`VariantMatrixAxisCard`, replacing two copies of card chrome that had already drifted apart), option values two-up instead of one tall column (chunked **column-major**, so the reorder arrows still move a value vertically), and a photo strip per option value in the mapped summary. **Reordering became one grip** — arrows deleted on the owner's call — and the grip is a `<span role="button">` because **a `<button>` is not a reliable native drag source**: a spike against a bare `<button draggable="true">` never fired `dragstart` in Chromium while identical markup as a `<span>` did. `keepFocusOffDisabledArrow` is deleted with the arrows; `DescriptionBlockEditor` still has the underlying problem and never used it. **A per-value photo needed no schema change** because `product_variant_option_values` already existed and the read model already joined it: one field (`optionValueId`) added to an existing `select` carries the link. But one photo still cannot belong to four variants — `variant_id` is one column and `(product_id, checksum)` is unique — so a chip is a control only where a value resolves to exactly one variant. **Two consequences accepted on the owner's explicit call**: the order of Variant Matrix values cannot be changed on a touchscreen (native drag fires from neither keyboard nor touch, and WCAG 2.5.7's single-pointer alternative is absent — closing it needs pointer-event dragging), and a group photo leaves the frozen order-line image falling back to the product primary for a different size of the same colour. **Also corrected in passing**: the claim that a group photo would leave a colour's other sizes "photoless on the storefront" is **wrong** — the PDP gallery is product-level and variant-tagged media only sorts after it, so ADR-007's order-line image is the only real exposure. See [[sals3-session-2026-08-22-part70-variants-and-pricing-rework-and-the-button-that-cannot-drag]]. - **Buyer reviews are built end to end, and their tables still do not exist in production — 2026-08-22, `sals3-portal` [#174](https://github.com/Sals3-Official/sals3-portal/pull/174) + [#176](https://github.com/Sals3-Official/sals3-portal/pull/176) and `sals3-ecommerce` [#150](https://github.com/Sals3-Official/sals3-portal/pull/150), all merged.** **Supersedes this cache's earlier "tables and nothing else" entry, which described #174 alone and was true for one afternoon.** What exists now: `sals3_product_reviews`/`sals3_product_review_replies`, the `modules/reviews/` domain, `POST /api/storefront/reviews` and `GET /api/storefront/products/[id]/reviews`, `rating` on the feed and detail payloads (cache keys bumped feed `v2`→`v3`, product `v4`→`v5`), the Seller Center **Product Reviews** screen under Dropship Catalogue gated on `review:reply`, and on the storefront: stars on cards, a Ratings-and-reviews PDP section, the per-line review control on the order **detail** page, and the form at `/orders/[orderNumber]/review/[lineId]`. **What is still not true: no review row exists anywhere, because `Reviews Migrate Product Reviews` (`workflow_dispatch`, `CRON_SECRET`) has not been run.** Both deploys are safe in that state on purpose — see the degradation rules below — but the feature does nothing until it runs, and the evidence to trust is `tablesExistAfter` true for both tables, never a green workflow. **The gate**: `fulfillment_groups.parcel_state = 'DELIVERED'` for the *item's own* package (ADR-008 splits one checkout per provider, so one order can hold a delivered package beside a moving one); `TRACKING_CONFLICT` deliberately does **not** qualify (ADR-004 §5 — a carrier "delivered" CJ disputes means we do not yet know it arrived). Eligibility is **derived, never stored**: no invitation table, no flag on the order line, accepted cost being that a reminder email has nowhere to hang. The buyer-facing control has **four** states, because a not-yet-delivered parcel and a closed window are different news and neither is a disabled button. **The wire carries a choice, not a name**: `attribution` is `named`/`anonymous` and the portal derives the published string from the order's own checkout ship-to, masked — the first cut sent a `displayName`, which is a way to publish any name against any purchase, and `BuyerSession` was deliberately left carrying only a uid and an email rather than widened for a form label. **`ratingLine` stopped being a non-claim** and is now derived from `rating`; shipping `4.6` beside "No reviews yet" in one payload would have let either half be quoted. The aggregate is a `GROUP BY` and **not** a rollup — it cannot drift from the list beneath it, and a hidden review leaves the list and stops counting in the same breath; revisit at ~50k reviews. A rating **gates nothing** (ADR-010 reserves `products.score`), a seller answers once (versioned, compare-and-set) and can never hide a review (`review:moderate` is the Admin Portal's, ADR-014), and no row can originate from a supplier (ADR-013 §7, ADR-017). **`review:reply`/`review:moderate` already existed in `PORTAL_PERMISSIONS` unused** — nothing was added to the permission model. **The defect that mattered, found only by checking before merge**: `buyer-read.ts` queried the review table on every buyer order read, unguarded, which in production would have `42P01`'d order history for every buyer who has ever paid. `verify` was green twice locally and on CI in both repositories while that was true. Now degraded at that one call site — controls vanish, the receipt does not — with `readOrUnavailable` deliberately **not** widened, because a portal-wide helper that swallowed `undefined_table` would hide schema drift everywhere. See [[sals3-session-2026-08-22-part69-buyer-reviews-shipped-and-the-read-that-would-have-taken-orders-down]] and [[sals3-session-2026-08-22-part68-product-reviews-schema-and-the-purge-edge]].

- **The Product Catalogue is eight columns and opens on `Live` — 2026-08-22, four owner reports, `sals3-portal` [#172](https://github.com/Sals3-Official/sals3-portal/pull/172).** Presentation and default state only: no schema, migration, server action, publish gate, permission, or CJ call changed. (1) **Publish and pause moved into the row's `More` menu.** The Actions cell was `Edit` + a `Publish to storefront` / `Pause listing` button + `More`, which made it the widest column on a nine-column table; the `overflow-x-auto` wrapper meant nothing was unreachable, but the edge landed mid-button and a control cut in half reads as broken rather than scrollable. The cell is now its own `CatalogueRowActions` component, which **owns the transition** — a `DropdownMenuItem` unmounts the instant the menu closes on click, and dispatching a transition from a component unmounting in the same commit is part 57's third production defect exactly; it is also why the outcome is a toast rather than a pending label. Collapsing the cell surfaced a latent defect: **one row had two meanings of Pause**, the real `unpublishProductAction` as a button and a preview-only in-memory pause as a menu item, both reading `Pause listing`. `productVersion` — the compare-and-set token the action requires — is now the discriminator, so a persisted row pauses for real and a fixture row says it is a preview. (2) **The `Availability` column and its `Any availability` select are gone.** `deriveProductAvailability` still runs for the `Out of stock (N)` filter and its count, and the expanded variant rows still show it per variant beside `supplierObservedQuantity`/`evidenceFreshness`/`lastCheckedAt`. **No ADR is contradicted** — ADR-013 §5 is *connection health*, not this, and §1 governs evidence preservation, which is untouched; what it supersedes is [[sals3-session-2026-08-10-part23-catalogue-dropshipping-alignment]]'s three-columns correction, whose substance (four separate dimensions, not one Active/Inactive flag) still stands. (3) **`Media` reads `Supplier photo`, not ADR-011 §4's `Supplier fallback`**, tone `warning` → `info`: `mediaStatusOf` returns `SUPPLIER_FALLBACK` for any published product carrying only the supplier's photo, so the column was putting an amber pill and the word "fallback" on nearly every row in production, contradicting §4's own "not a customer-facing warning" sentence. Recorded on `MEDIA_STATUS_LABELS` and in ADR-011's `Amendment — 2026-08-22`, same handling as the sticky panel and the micro-labels. (4) **The screen opens on `Live`**; `All` stays leftmost and the counts are unchanged, and a catalogue that is entirely drafts deliberately lands on the empty state rather than have the landing tab depend on data. `npm run verify` green (2,363 unit, 79 e2e) and CI green. **Not proven against real rows**: the local database has no listings, and the Vercel preview is behind Vercel SSO, so the pill, the menu contents and publish/pause are unit-tested rather than browser-verified — needs a signed-in seller. Also open: an `ARCHIVED` row is still offered `Publish to storefront` (pre-existing), and nothing asserts the row's action set in a test. See [[sals3-session-2026-08-22-part67-the-catalogue-column-that-was-doing-nothing]].

- **The PDP's option label is sentence case at 13.5px, against its own build spec — 2026-08-22, owner decision, [#146](https://github.com/Sals3-Official/sals3-ecommerce/pull/146) merged (`aa29fd2`).** It reads `Colour: Pink` — axis name in Plus Jakarta Sans 500 13.5px `ink-muted`, chosen value 700 `ink`, no caps and no tracking, shared by all four labels (the two axis rows, `Choose an option`, `What we know`) through `PRODUCT_MICRO_LABEL` in `product-label-styles.ts`. The colon belongs to the label's text, not the value's class, so an axis with nothing chosen renders `Colour` and never a dangling `Colour:`. Live-verified after merge: `Plus Jakarta Sans | 500 | 13.5px | normal | none | rgb(69,78,85)` with the value at 700 `rgb(20,24,28)`; label contrast **improved** from 5.3:1 to 8.6:1. **`hot.md` said Outfit 600 for one afternoon and that is now wrong** — see the corrected history below, and [[sals3-session-2026-08-22-part66-the-font-that-was-never-the-problem]]. **How it got here, because the wrong half of it is quotable:** [#144](https://github.com/Sals3-Official/sals3-ecommerce/pull/144) (merged `746745b`) first moved these labels to **Outfit 600 at 11px caps** and is **superseded**. The owner boxed `COLOUR Black` and `SIZE L` on production and asked for the PDP's designated font. Measured first, and the labels were **already correct**: Plus Jakarta Sans 11px/700, which is what `PDP_REDESIGN_V3_1_BUILD_SPEC.md` line 400 designates ("Outfit display, Plus Jakarta Sans body"), what the `.dc.html` prototype specifies by carrying no `font-family` at all on that label, and what `WHAT WE KNOW` three rows below — byte-identical in computed style, and not boxed — also rendered. Both webfonts reported `loaded`, so this was not part 62 recurring. So the report could only be satisfied by **changing the design intent**, which needed the owner rather than a diff: Outfit 600 on the label *and* the chosen value beside it, across **all four** micro-labels (the two axis labels, `Choose an option`, `What we know`), because they share one class list and moving only the boxed two would have put two identically-styled labels in two faces in one panel. The class list is now one exported string in `product-label-styles.ts` whose doc comment records the override so the next agent does not reconcile it back — same handling as the sticky panel in part 64. That first answer measured correct on production and was still wrong to look at, because **the family was never the problem**: an 11px label in caps with `0.08em` tracking is thin and small in any face, and the mixed-case value glued to it put two letter cases in one short line. ### ~~Hard-coded exchange rate~~ - fixed 2026-08-07 (fourth session)

`CJ_USD_TO_PHP_RATE` was a hand-typed `58` while the real rate had moved to ~`61`. Because the markup sits on top of a fixed conversion, the drift came straight out of margin: an intended 30% was really earning **~23.7%**, about ₱28 per unit on a ₱550 item, with nothing reporting it. **Fixed**: `src/lib/storefront/fx.ts` fetches the European Central Bank's published reference rate (Frankfurter, falling back to `open.er-api.com`) and adds `CJ_FX_BUFFER_PERCENT` on top — money-changer logic, because a mid-market rate is a wholesale number nobody can transact at. ECB publishes once per business day on purpose, so shopper prices move at most daily. Fails safe: 4s timeout, second source, rejects a rate outside 30–120 or >10% from last known good, then last-good, then the configured fallback, logging `[storefront-fx]` when it degrades. `CJ_USD_TO_PHP_RATE` is now only the fallback.

The buffer shipped at **2.5%**, sized from card/PayPal rail costs (PH credit card ~1.85%, PayPal 3–4%) because the actual payment route was unconfirmed. **Settled 2026-08-08 (owner decision)**: Bogs confirmed CJ Wallet, topped up by wire/Payoneer, is the real payment method — not per-order card or PayPal. That number is now stale evidence for the wrong rail and needs re-deriving from a real wallet top-up statement (transfer fee + FX movement headroom), not the card/PayPal comment still in `src/lib/storefront/fx.ts`. Code not yet updated — see [[sals3-session-2026-08-08-part19-owner-decision-cj-wallet-and-multi-supplier-roadmap]].

**Rate source settled 2026-08-07**: ECB stays, and the earlier "should this be BSP instead?" question is closed. Bogs stated that the stakeholders handling money are Australian, so a Philippine central-bank rate is not the natural anchor for the books — an internationally recognised reference rate is. Note this also means a **second FX exposure exists that this code does not touch**: shopper pricing converts USD → PHP, while the company's books would sit in AUD, so supplier cost in USD and revenue in PHP both have to land somewhere in AUD. That is an accounting question for whoever owns the ledger, not a storefront-pricing one, and it connects to the unresolved jurisdiction item under Active risks.

**This fixes one input, not the pricing.** The 30% markup still excludes freight, payment fees, returns, and duties, so it remains a flat markup where [[ADR-003-international-availability-shipping-and-pricing]] calls for landed cost and contribution economics — still blocked on approving a destination market, because freight is destination-specific.

### Jurisdiction and market configuration

## Reusable lessons

See [[sals3-skills]] for the detailed engineering lesson register. Continue to verify against actual code/data, keep source contracts strict, avoid fabricated public claims, and report exact validation evidence rather than assumed behavior.

**`revalidatePath(path)` invalidates that one page, not the routes beneath it** (learned 2026-08-25, on the variant photo that would not stay). Nine action files pointed at `/listings` while the screen the seller was standing on was `/listings/new?productId=…`, so every editor write committed to Postgres and then read back stale — the optimistic thumbnail appeared and the refresh removed it. The general rule is not "add the child path": it is that **a hard-coded list of paths is correct only until a route moves, and nothing reports the day it stops being correct**. Use the `'layout'` second argument to invalidate the subtree, in one shared helper, so the rule cannot be applied to eight call sites out of nine. Watch for the assertion that hides it too — `toHaveBeenCalledWith('/listings')` passes for the broken single-argument call, so pin the argument.

**Ask what a new subscriber does *not* hear.** The PDP gallery was made to follow the selected variant over the event the option chips already broadcast — correct, minimal, and it inherited a gap: `ProductRecordPanel.handlePopState` updates its own state without dispatching that event, so the browser back button moved the panel and not the gallery. Nothing had desynced before, because the gallery did not follow variants at all; **adding the behaviour is what created the gap**. Whenever a component becomes the second or third listener on an existing signal, enumerate every path that already changes the underlying state and check which of them skip the signal.

**A decorative field must not be able to delete a commercial row.** `variants` on the storefront consumer is a `salvagedArray`, which drops a whole row when any field fails validation. Adding `imageUrl: z.string().url().optional()` therefore meant one malformed address cost a buyer a size they could no longer choose, to avoid a missing thumbnail. Salvage granularity has to match what the field is worth: `.catch(undefined)` at the field, not row-level rejection. The doc comment had described the drop as though it were the design — it was not, it was unexamined, which is the same failure as part 69's `ratingLine`.

**Derive a group's answer once, in the producer.** `product_media_sources.variant_id` holds one id and the `(product_id, checksum)` index forbids a second row for the same file, so one photo cannot belong to four variants and the editor's group control writes it onto one of them. Serving that column raw would have every consumer re-derive the grouping, and the first one to skip it ships `Black · S` with a photo and `Black · M` without. `shareFirstAxisPhotos` resolves it before the wire — the same argument that made the review aggregate a `GROUP BY` rather than a rollup: one answer that cannot disagree with itself.

**When a change falsifies a comment, the comment is now a defect.** `VariantValuePhotoStrip` refused to make a shared value a control and explained why in prose that `shareFirstAxisPhotos` made untrue in the same session. Leaving it would have been part 69's `fetchProductReviews` on purpose. Removing the lock also exposed a contradiction nobody had recorded: the Variants & Pricing rail had always done exactly what that panel called impossible.

**Drizzle names every column of the schema in an `INSERT`** (learned 2026-08-21, the hard way, on the order table). Omitted columns are filled with `default`, so adding a column to a Drizzle table is by itself enough to change the SQL every writer of that table emits — there is no "define it now, write it later". A column can only ship a release ahead of its reader if it is absent from the schema file too, which means the `drizzle/` migration file and its `__drizzle_migrations` row have to travel with the *schema* change, not with the DDL. `sals3-portal`'s `order-line-columns.test.ts` pins this with a `toSQL()` assertion, and the same rule governs `product_media_sources`. Related: a bare `.select()` expands to every schema column for the same reason — name the columns on any table that is about to grow one.

**A green suite says nothing about a table your local database does not have** (learned 2026-08-22, the hard way, on the buyer orders API). `npm run verify` passed twice locally and on CI in both repositories while `buyer-read.ts` queried `sals3_product_reviews` on every order read — a table that exists in neither the local database *nor* production. The local database is empty, so the query was never exercised; production has the order tables but not the review one, so it would have `42P01`'d order history for every buyer who has ever paid. Two rules fall out of it. First: **a new read on an existing path inherits that path's blast radius**, so after adding any query to a working reader, ask what it just made as fragile as its newest table. Second: because DDL reaches a deployed database through a `workflow_dispatch` and not through the deploy, there is *always* a window where the code exists and its tables do not — a new read must either survive that window or be gated by something stronger than a sentence in a PR body. Probe `information_schema` before reasoning about which tables a database has; do not infer it from the suite.

**Degrade at the call site, never in the shared helper.** `readOrUnavailable` treats only connection-class SQLSTATEs as unavailable and rethrows the rest, and that is correct: adding `42P01` to it would make one portal-wide helper swallow `undefined_table` everywhere and hide exactly the schema drift the PR #102 incident was about. The catch belongs at the one call site that has decided it can live without the answer, with a comment saying what it is trading. Corollary from the same session: a missing table must read as a **migration gap**, not as an outage — `/reviews` checks for its own tables and names the workflow rather than rendering "the database did not respond".

**A doc comment that describes intent while the code does the opposite is worse than no comment.** `fetchProductReviews` said it answered `[]` rather than throwing, and threw — `requestStorefrontJson` raises on a non-2xx and on a malformed envelope, so a portal 503 would have taken out the whole product page. Nothing in the suite contradicted the comment because nothing tested the claim. When a function's doc promises a failure mode, that promise is a test case.

**Two fields describing one fact must derive one from the other.** `ratingLine` was a fixed "No reviews yet" while `rating` carried a real average, which would have put two contradictory answers in one payload and let either be quoted as current — the same failure part 61 recorded in this cache. Derive, or delete one.

**A caller-supplied display string is a caller-supplied identity.** The first review submission sent `displayName`, which is a way to publish any name against any purchase; validation cannot repair it because the value is still the caller's. The wire now carries a *choice* and the server derives the string from data the order already holds. The alternative — widening `BuyerSession` past its documented uid-and-email surface — would have traded a security boundary for a form label.

**Adding a foreign key is a change to every existing delete path, not only to the new table** (learned 2026-08-22, the mirror of the rule above). A new `REFERENCES ... ON DELETE restrict` makes an existing `DELETE` illegal without touching a line of that deleting code, so nothing typechecks, lints, or tests differently — `sals3-portal`'s `verify` was green twice and CI passed while `purge-catalogue-products.mts` had already been broken by a new edge onto `products`. Worse, it is invisible while the new table is empty and only bites once real rows exist, which is long after anyone connects the two changes. After adding any FK, sweep for `delete from <referenced table>` and `.delete(<table>)` across `src/`, `scripts/`, and `e2e/` and ask which of them the new edge now forbids. The question `verify` never asks is *which existing path did this make illegal?*

**A migration whose statements are individually idempotent needs a transaction per statement, not one for the run.** `CREATE TYPE` and `ALTER TABLE ... ADD CONSTRAINT` have no `IF NOT EXISTS` form, so re-runnability comes from catching Postgres `42710`/`42P07`/`42701` — and a `catch` inside one shared transaction is useless, because the first already-existing object aborts the transaction and every later statement fails on a poisoned connection. The `catch` has to sit outside the transaction. This passes every test that only ever runs against a fresh database, so it is a review question rather than a test one.

**`UPDATE ... RETURNING` in Postgres reports the row *after* the statement.** It cannot supply the previous value, so an audit trail that needs the origin must read before writing.

**Prove an endpoint is deployed before calling it.** An unauthenticated request returning `401` rather than `404` is the cheap proof the route exists; a green deployment status is a different claim. Used before every break-glass POST on 2026-08-21.

**Mergeability is not verifiability.** GitHub reporting a PR mergeable means only that there is no text conflict. For anything on the money path, merge the base in locally, run the full suite against the actual merged tree, and let CI see that commit.
