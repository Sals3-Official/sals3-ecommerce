## 1. Owner decision this implements

Per `CLAUDE_TURNOVER_CATEGORY_MARGIN_AND_FX_POLICY.txt`: margin is assigned primarily **per Sals3 category** — the normal operational default — not one mandatory global percentage. Product overrides are an explicit, justified exception; variant overrides are rare and need their own additional justification. FX adjustment is a separate, seller-owned buffer, never a category default and never the platform reference rate itself. Phase 1 does not touch checkout, CJ freight, payment, or tax, and does not pretend customer-paid shipping is decided.

## 2. What was built

**Schema** (`src/lib/db/schema/pricing-policy.ts`, migration `drizzle/0010_regular_scarecrow.sql`, generated but unapplied): `sals3_categories` (global reference data, seeded from the real Sals3 Taxonomy v0 workbook — see §3), `pricing_category_policies`, `pricing_product_overrides`, `pricing_variant_overrides`, `pricing_fx_adjustment_policies`. Every policy table is append-only-by-edit: an edit inserts a new row and marks the previous one `SUPERSEDED` in the same transaction; a partial unique index (`WHERE status = 'ACTIVE'`) makes "the current policy for X" a single row the database enforces, not an application convention — schema-level tests (`pricing-policy.test.ts`) assert the partial-index `WHERE` clause survives, the same pattern `supplier-connections.test.ts` already uses to guard the CJ-connection uniqueness rule. Overrides are keyed to `supplier_candidates.id`/a plain CJ variant-id string, **not** a `products`/`product_variants` table — no such table exists anywhere in this codebase (confirmed: no Product/Variant/Offer model is built). This anchors overrides to the one real, persisted, tenant-scoped "this is a specific product a seller is sourcing" identity that exists today, matching this codebase's own stated precedent for `supplier_candidates` itself ("modelling them before the flow that fills them would be schema for its own sake"). It will need a follow-up migration once a real Product table lands.

**Money/rate math** (`src/modules/pricing/money-math.ts`): pure BigInt fixed-point arithmetic — no `decimal.js` dependency added, matching the codebase's existing plain-integer-minor-units convention. A rate is stored as Postgres `numeric` (Drizzle returns it as a `string`, never a JS `number`) and parsed into a `RATE_SCALE`-scaled bigint before any arithmetic. `NEAREST_0_99` rounding always rounds *up* to the current major-unit bucket's `.99` (13.00 → 13.99, 12.99 unchanged, 13.01 → 13.99) so it can never quote below the resolved margin — charm pricing, not a fabricated comparison price (ADR-003 §5 bans the latter, not the former). BigInt literals (`0n`) could not be used — the project's `tsconfig.json` targets `ES2017`, and bumping that project-wide for one module was out of scope, so every constant is built with `BigInt(...)` instead.

**Resolver** (`src/modules/pricing/resolver.ts`): resolves category → product override → variant override (most specific wins), applies the seller's FX adjustment on top of the platform reference rate, and returns a typed `PRODUCT_MARGIN_ESTIMATE` or a specific `PRICING_UNAVAILABLE` reason (`CATEGORY_MAPPING_REQUIRES_REVIEW`, `CATEGORY_POLICY_REQUIRED`, `SUPPLIER_COST_UNAVAILABLE`, `REFERENCE_FX_UNAVAILABLE`, `FX_ADJUSTMENT_POLICY_REQUIRED`, `POLICY_EXPIRED`, `INVALID_MARGIN_RATE`) — never a fabricated number. Server-side only; never trusts a browser-supplied margin, rate, cost, or policy id.

**Reference FX** (`src/modules/pricing/reference-fx.ts`): deliberately **not** `src/lib/storefront/fx.ts` (real production storefront checkout pricing, a different currency pair and an already-reviewed surface) and **not** `src/lib/products/catalog-fx.ts` (explicitly documented as design-preview-only fixture data). No reference-FX provider is approved for the Portal's own pricing surface today, so this returns the identity rate (`1.0`) for a same-currency pair only — the common case, since ADR-003 phase 1 is USD-only — and `null` for every other pair, which the resolver turns into `REFERENCE_FX_UNAVAILABLE` rather than inventing a number. **Consequence worth flagging**: this makes the entire FX-adjustment-policy branch (funding-rail requirement, policy lookup, expiry check, the actual adjustment math) currently unreachable through the real code path, since no cross-currency pair can ever produce a non-null reference rate yet. It is real, tested code (via a test that mocks `reference-fx.ts` to simulate a future approved provider — the same forward-declared-but-unused pattern this codebase already uses for reserved enum values), waiting for that provider to exist.

**Taxonomy seeding**: `docs/Raw/universal_category_variation_taxonomy.xlsx`'s `Universal_Category_Taxonomy` sheet was read directly (via a one-off Python/openpyxl extraction, not checked into the app — only the frozen output is) and converted to `sals3-portal/src/lib/db/seed-data/sals3-taxonomy-v0.json`: all 1,345 rows, 29 distinct L1 departments, zero duplicate codes — independently re-confirming the exact counts ADR-002 already states as verified. `scripts/seed-sals3-taxonomy.mts` (idempotent, `onConflictDoNothing` on the unique code) loads this into `sals3_categories`; **not run** — it requires migration 0010 applied first, which this task explicitly did not authorize. A genuine, non-invented taxonomy gap surfaced while picking a category for the Product Editor's existing "Aurelis 20L Packable Daypack" fixture: no unisex/outdoor backpack branch exists in the real workbook, only gendered "Bags" departments (`Men's Bags & Tactical Backpacks > Backpacks`, `CAT-MEN-100564`) — used as the closest real code, marked `ACCEPTABLE` confidence rather than `EXACT`, not smoothed over.

**Server actions** (`src/app/(portal)/market-rules/pricing-actions.ts`): Zod-validated, `requirePermission('pricing_policy:manage')`-gated, rate-limited, every read/write scoped to the caller's own `sellerAccountId` inside one transaction with an `appendAuditEvent` in the same transaction — same discipline as `supplier-apps/actions.ts`. New permissions `pricing_policy:read`/`pricing_policy:manage` added only to `seller_manager` (mirrors `finance:read`'s existing role distribution — staff and viewer get neither). Product/variant override actions verify tenant ownership via the existing `candidateBelongsToSeller` join-based check (IDOR guard), not a caller-supplied seller id.

**UI**: Settings → Market Rules gained two new sections (`CategoryPricingSection`, `FxAdjustmentSection`) below the existing rules table, gated by `pricing_policy:read` independently of the page's own `market_rules:read` gate. No new top-level nav item. Product Editor's existing "Variants & Pricing" card gained a `PricingBasisPanel` above the existing `VariantPricingTable`, server-resolved in `page.tsx` per variant — the override action buttons are present but informational-only for every current fixture (`realSupplierCandidateId: null`), since the Product Editor is 100% mock/fixture data with no real candidate id to attach a real override to; the underlying action is fully real and tested against real candidate ids, just not reachable from this particular mock screen yet.

## 3. A real bug this work found and fixed in itself

Both new Market Rules sections and the Product Editor's pricing panel read real Drizzle tables (`pricing_category_policies`, `sals3_categories`, `pricing_fx_adjustment_policies`) that do not exist in this environment's database yet (migration 0010 deliberately unapplied). The first version of these components let that query throw uncaught, which crashed the entire `/market-rules` page render — caught by the **existing** e2e suite (`seller-center-market-rules.spec.ts`), not a new test, once it was run against this change. Fixed by wrapping each read in a try/catch that logs and degrades to an honest "not available right now" state, distinct from the real "no policy configured yet" empty state — the same discipline `resolveFixtureVariantGuidance` already used for the Product Editor path, and the same class of incident `connectCjSupplier`'s own code comment describes from 2026-08-10 (`supplier_account_bindings` reaching a deployment before its migration). Confirmed fixed by re-running the full e2e suite against the real local database with the migration still unapplied: 51 passed, 1 skipped, 0 failed.

## 5. What is still not done

- Migration 0010 not applied to any database; `scripts/seed-sals3-taxonomy.mts` not run.
- The FX-adjustment-policy branch is real and tested but currently unreachable in production, since no approved reference-FX provider exists for a non-identity currency pair (§2).

The resolver's return type already carries every field ADR-015 §7 requires; wiring it to real persistence is natural once a real publish/accept-order action exists to anchor it to.
